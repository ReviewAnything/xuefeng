# 设计评审：`设计的原点` × `整体页面布局与功能布局`

> 评审对象：两份文档（下称「原点」「框架」）
> 评审基准：仓库 `8a9ad7ebe8`（含结论页）
> 评审方式：读实现 + 起真实服务跑数据 + 逐条核对文档的技术假设
> 日期：2026-10-20

---

## 0. 结论（三句话）

1. **方向对，版式对，语义空。** 「矛盾探测器」是真实的差异化命题；但当前 `alignment` 是 `view` 的一个查表函数，数据侧只贡献一个布尔值。在对置双栏里放这个结果，是把"没有信息"包装成"数据支持/反驳了观点"。
2. **这份设计的验收话术，自己承认了它需要讲解。** 原文：「打开 → 切透镜 → 输入专业 → 指着对置双栏说'左边是观点，右边是数据，这里冲突，原因是……'」——这一句话就是讲解。以「从输入走到有主张的结果页，中途不解释」为验收线，它不通过；现有的结论页通过。
3. **时序反了。** 「框架」把版式（M1，3–4 天）放在数据之前，称 M1 是分水岭。真实的分水岭是 `school_lines = 0 行`——没有校线，对置版式没有第二侧可对。先做版式会得到一个漂亮但被追问就塌的空框。

---

## 1. 与验收标准对照：「不解释」测试

| 页面 | 需要讲解的概念 | 讲解成本 | 判定 |
|---|---|---|---|
| 现有结论页 | 无（一句判断 + 三个动作 + 一条红线） | 0 | 通过 |
| 「原点」核验页 | ① 透镜是什么 ② 置信度徽标为什么两种 ③ 冲突为何发生 ④ 观点与数据口径不同 | 4 个 | **不通过** |
| 「框架」核验页 | 同上 + ⑤ 为什么两栏不对齐 | 5 个 | **不通过** |

「原点」自己写：「这句话是产品的灵魂，必须用正文大字，放在结论横幅正下方」——那句"灵魂句"是**解释文本**，不是结论。一个需要 40 字解释才能自洽的结论，不是结论。

**这不是说对置版式错了**，而是说：对置版式成立的前提是两侧可对置。现在不可对置（见 §2.2），所以只能靠解释把缝糊上。

## 2. 合理性

### 2.1 成立的部分（应当保留）

| 判断 | 为什么成立 | 仓库现状支撑 |
|---|---|---|
| 不做「好看的志愿工具」 | 推荐列表是红海，夸克/百度已占位；「把矛盾摆出来」没人做 | 无竞品对标，属真空 |
| 置信度一等公民 | 仓库已区分 `official(11省)/estimated(20省)/sample`，界面理应同步 | `data_source` 已全链透传，只差视觉权重 |
| 冲突优先于和谐 | 批量核验后端已按 冲突→谨慎→一致 排序 | `verify_many` 已实现，前端未表达 |
| 观点侧 / 数据侧物理对置 | 比"结论卡"更难伪造：两张牌各自露出牌面 | 无 |
| 观点侧暖 / 数据侧冷 | 用温度差编码"判断 vs 事实"，是版式语言而非装饰 | 无 |
| 管理端不参与重设计 | 用户是运营者，不是考生 | 管理端已是 Element Plus 默认风格 |

### 2.2 不成立的部分（核心问题）

#### 问题 A：对置的两侧不是同一个命题

- **观点侧**回答：这个专业**值不值得读**（就业面、内卷度、家庭资源依赖）。
- **数据侧**回答：你这个位次**够不够得上这一档**（批次门槛）。

二者可以同时为真，不构成矛盾。「原点」给的招牌例子——

> 张雪峰说慎选，但你的位次够得上

——是 category error：慎选的原因是就业，够得上是录取。这句话读起来像发现了一个矛盾，实际是把两个无关事实并排摆放。**「原点」把这句话定为"产品的灵魂"，而这句话本身是逻辑空转。**

仓库自己已经承认了这一点。`shared/content.json` 的 `CONTENT_SOURCE.caveat`：

> 观点为定性判断、数据为定量口径，**二者口径不同**；交叉核验结果仅供学习参考……

设计与代码在同一个问题上互相矛盾。

#### 问题 B：`alignment` 是 `view` 的确定性函数（实测）

38 个专业 × 4 个位次场景，批量核验结果：

| 场景 | 可及档位 | 一致 | 需谨慎 | 冲突 |
|---|---|---|---|---|
| 河南 物理类 28500 | 985 × 38 | 18 | 20 | **0** |
| 河南 物理类 120000 | 普通一本 × 38 | 18 | 20 | **0** |
| 广东 物理类 40000 | 一本 35 / 985 3 | 18 | 20 | **0** |
| 广东 物理类 300000 | 二本 21 / 专科 17 | 0 | 21 | **17** |

对照 `view` 分布（recommend 18 / avoid 17 / caution 3）：

```
可及档位 ∈ {二本, 专科}:  recommend→caution  caution→caution  avoid→conflict
可及档位 ∉ {二本, 专科}:  recommend→aligned  caution→caution  avoid→caution
```

**六格查表。** 数据侧的全部贡献是一个布尔：「你的位次是否落在二本/专科」。把它画成红色冲突横幅，等于把一个 if 渲染成一次科学发现。

#### 问题 C：冲突只对最弱势的用户亮红灯

- 尖子生（河南 28500，985 可及）：**0 冲突**，18 条全是"一致"。页面会告诉他"数据支持全部推荐专业"——这是一句没有信息量的恭维。
- 二本/专科段（广东 300000）：**17 条冲突**，文案是"建议坚决规避或仅作保底"。

红色警报只对最没有腾挪空间、且数据最不可靠（这批省份多为 `estimated` 推算基线）的用户亮起。这是设计伦理问题，不只是算法问题。

#### 问题 D：观点侧与数据侧的证据等级倒挂

界面把两侧做成**等权重对置**（左栏右栏同宽同高），但：
- 观点侧：手写定性判断，无逐条出处（`content.json` 自述"后续可逐条细化到具体出处"）。
- 数据侧：11 省官方省控线 / 20 省参数推算。

等权重版式隐含"两方证据强度相当"。实际是"无出处的手写观点" ≈ "参数推算的估算线"。**置信度原则只加在数据侧（原则 3），却没加在观点侧**——观点同样是分级的（本人公开表述 / 社区整理 / 二手转述），文档没处理。

## 3. 持续性

### 3.1 人格依附

产品主标签叫「张雪峰框架」。三个后果：

1. **法律面**：以真实姓名作为产品主标识（栏目名、徽标、tab 文案），涉及姓名权/商标风险；一旦对方不认可"代言式"呈现，改名成本是全站文案。
2. **可证伪面**：他的公开立场会变。你的 38 行是静态的，一张截图就能证明"他后来改口了"，而你的界面还写着"张雪峰视角：避坑"。
3. **扩展面**：第二个观点来源（如某高校教授、某行业报告）无法接入——因为框架被绑定在一个人身上，不是一套方法。

**可持续的做法**：把人格抽象成方法论。
- 透镜名改为「就业确定性优先」/「兴趣与长期匹配」，张雪峰作为**观点来源之一**出现在每条 `view_source` 里，而不是出现在产品名里。
- 每条观点必须带：`view_source`（本人/社区/二手）、`reviewed_at`、`expires_at`。

### 3.2 内容治理缺位（最严重）

仓库花了 D1–D4 为**分数**建了完整治理：`data_versions` 状态机、`validate_year` 校验、`data_changes` 审计、`official` 必带 `source_url`。

而**差异化资产（观点表）在治理之外**：
- 存放于 `shared/content.json`，无 `source_url` 字段，无复核期限；
- 不在 `data_versions` 里，`validate_year` 不检查它；
- 年度更新只 bump `APP_VERSION`，没有任何机制检测"数据变了、观点该复核了"。

结果是：分数年年更新，观点原地不动，`alignment` 随年份漂移（去年 aligned 今年 conflict），无人复核、无人告警。**这类漂移不会报错，只会静默失真**——比崩溃更难发现。

### 3.3 覆盖与分布

| 指标 | 现状 | 判断 |
|---|---|---|
| 专业覆盖 | 38 / 约 800（4.8%） | 「图谱页做供给入口」不成立——供给只有 38 张卡 |
| view 分布 | recommend 18 / avoid 17 / caution 3 | 47% 是"避坑"，图谱近半是黑名单 |
| 更新频率 | 观点一次写成，无版本 | 二次打开无新内容 |

「框架」把图谱页定为 tab2「供给入口」，但没算一件事：38 张卡，用户滑两次就到底。要么扩到 200+（内容运营成本），要么图谱不该占一个 tab。

## 4. 可行性（逐条核对文档的技术假设）

### 4.1 硬错误：`--td-brand-color` 不属于 wot-design-uni

「原点」建议在 `uni.scss` 覆盖 `--td-brand-color` 等变量。实测：

```
$ grep -rhoE '\-\-(wot|td)-[a-z0-9-]{3,}' node_modules/wot-design-uni | sort | uniq -c
   2 --wot-sort-button-height
   2 --wot-slide-verify-track-width
   ...（全部为 --wot-*，无一条 --td-*）
```

`--td-*` 是 TDesign 的命名。wot-design-uni 用 `--wot-*`，且本仓库的真实主题机制是：

```vue
<wd-config-provider theme="dark" :theme-vars="themeVars">
```
```js
// src/utils/theme.js —— camelCase JS 对象，注入为 CSS 变量
export const themeVars = { colorTheme: "#ffd24d", darkBackground: "#16191f", ... }
```

在 `uni.scss` 写 `page { --td-brand-color: ... }` **不会生效**。正确路径只有两条：扩展 `themeVars`（现有机制，全端生效），或在 `App.vue` 全局样式里定义 `--xf-*` 供自定义组件消费。**「半天落地 token」按文档写法是 0 天效果。**

### 4.2 硬冲突：浅色配色 vs 深色仓库

| | 文档建议 | 仓库现状 |
|---|---|---|
| 页码底色 | `#F7F3EC` 暖米白 / `#F0F4F8` 冷灰蓝 | `#0f1115` |
| 主色 | `#1F3A5F` 深海军蓝 | `#ffd24d` 金 |
| 文字 | 深字浅底 | 浅字深底（`#e6e8ec`） |

「原点」说"不推倒重来"，但给的是一套**浅色皮肤**。二选一：
- 转浅色 = 重写 9 页全部配色（不是"半天"）；
- 保留深色 = 温度差要重新推导：观点侧暖暗 `#241f14`，数据侧冷暗 `#131a24`。文档的颜色值一条都用不上。

### 4.3 规模被低估

| 项 | 实测 | 文档假设 |
|---|---|---|
| 页面硬编码色值 | 195 处（verify 44 / verdict 29 / majorGroup 24 / majors 23 / recommend 22 / diagnose 20 / plan 18 / about 8 / resources 7） | 视为可"token 化"的小改 |
| 字号种类 | 13 种（20/21/22/23/24/25/26/27/28/30/40/64rpx） | 收敛到 4 档 |
| 圆角种类 | 7 种（6/8/10/12/14/16/999rpx） | 收敛到 2 档 |
| tabBar | 5 格（结论/专业/核验/资源/关于） | 改为 3 格 |

「8rpx 网格、四档间距、两档圆角」= 全站样式重写。M1 估 3–4 天，实际系数 2–3。

### 4.4 文档的"现状"已过期一个提交

「框架」的判断前提是：

> 现状（错误）：五页面平铺，用户先选功能再输入

实际（`8a9ad7ebe8`，本轮刚推）：9 个页面，结论页已是首页与首个 tab，输入省份/科类/位次直接出一句判断 + 三个动作。**「核验页做首页」这个核心决策，仓库已经用一个更硬的版本实现了**——只是它答的是"你能上什么档次"，不是"这个专业值不值"。

两份文档都没有这个页面。它们的 IA 是围绕一个已被超越的假设设计的。

### 4.5 tab 结构：3 tab 方案本身有问题

1. **志愿表占 tab 是浪费**：空容器页（无草稿时）占掉 1/3 注意力。它应该是结论页的下钻终点，不是平级入口。
2. **结论/核验拆两个 tab 是切断链路**：位次 → 档位 → 专业是**串行深度**，不是并列功能。tab 的定义是"互不依赖的并列入口"，把它们平级化，等于把一条路径的两段切成两个抽屉。
3. **资源/关于并入设置**（文档提了）——这条是对的，5 格确实过密。

### 4.6 唯一的硬约束：`school_lines = 0 行`

```
$ school_lines rows = 0
```

- `recommend/schools` 的 `school_line_hits` 全为 0，所有院校行 `min_score = null`。
- 没有校线 → 没有"某校某专业组近三年位次" → 数据侧无法回答"这个专业在你这个位次是否真的可及（校名级）"。
- **对置版式的第二侧，现在是空的。**

「框架」把 M1（版式）定为分水岭，M1 的验收是"指着对置双栏说左边观点右边数据"。这一条在没有校线的今天是**可以演示但不可追问**的——被问"哪个数据支持这条观点"，答案只能是"你够本科线"。这正是上一轮要求消除的那种"需要解释才能成立"。

## 5. 时序：版式不是分水岭，可对置性才是

```
文档顺序：token → 组件 → 对置版式（M1 分水岭）→ 批量 → 图谱 → 志愿表 → 透明度
实际依赖：语义（数据侧回答什么）→ 数据（能否回答）→ 版式（把答案并排）→ 交互
```

版式是**放大器**：语义成立时它放大可信度，语义空转时它放大虚假确证。现在放大的方向是后者。

## 6. 落地方案

### L0 语义层（必须先做，1–2 天）

**给"数据侧"定义一个与观点同命题的量。** 观点说"这个专业慎选"，它隐含一个可检验的推论。三选一：

| 数据侧候选 | 与观点的关系 | 数据可得性 | 结论 |
|---|---|---|---|
| 录取位次 3 年趋势 | "热度在退/涨"——直接支撑或反驳"慎选" | 需 2 年以上校线，**现为 0 行** | 首选，但受阻 |
| 招生计划增减 | "供给在扩/缩"——支撑"内卷/过剩" | 需新增 `enrollment_plans` 表 | 次选，可先行 |
| 批次门槛（现有） | **与观点无关**，只能表达"可及性" | 已有 | 不能用于判冲突 |

**规则化改造**（关键）：
- 把 `alignment` 从 `(view, tier_low?)` 查表改为**证据规则**：`观点命题 P` × `数据趋势 T` → 支持/反驳/无证据。
- **引入证据门槛**：双侧证据不齐时，`alignment = "unverified"`，界面退化为单栏 + "数据未覆盖"，**不出现冲突横幅、不出现"一致"**。
- 现有 6 格查表降级为 `reachability`（可及性提示），与 `alignment`（证据一致性）**拆成两个字段**，UI 上不再并排同等重量。

**验收**：新增测试断言——`school_lines = 0 时，任何专业不得返回 conflict/aligned`。这一条通过，才允许动版式。

### L1 观点治理（2 天）

| 动作 | 具体 |
|---|---|
| 字段扩展 | 每条观点加 `view_source`（本人公开表述/社区整理/二手转述）、`source_url`、`reviewed_at`、`expires_at`、`evidence_grade`（A/B/C） |
| 入状态机 | `MAJORS` 纳入 `data_versions` 校验，与 `admission_baselines` 同等待遇 |
| 去人格化 | 产品文案「张雪峰框架」→「就业确定性优先」；人名降级为 `view_source` 的取值 |
| 漂移告警 | 数据年度更新后，自动列出"依赖该数据年份的观点"清单，进复核队列 |
| 置信度双向 | `ConfidenceChip` 同时标注观点等级与数据等级（文档只做了数据侧） |

### L2 版式层（3–5 天，依赖 L0 有数据）

按「原点」的组件设计做，但三处改：

1. **深色温度差**：`--xf-opinion-bg: #241f14`（暖暗）/ `--xf-data-bg: #131a24`（冷暗）。冲突色 `#C0392B` 在深底上偏暗，改 `#E05A4A`。
2. **token 路径**：扩展 `theme.js#themeVars`（全端生效）+ `App.vue` 全局 `--xf-*`，不碰 `--td-*`。
3. **降级态**：`OppositionPanel` 必须支持 `side="single"`——一侧无证据时整栏收起，另一侧占满 + 顶部"数据未覆盖"条。文档缺这个状态，是它最大的实现风险。

### L3 结构层（2 天）

不推 3 tab。保持串行：

```
tabBar: [结论] [专业] [志愿表]        ← 3 格，但第三格是"容器"，有草稿才高亮
        （核验 = 结论页向下钻的第二层，不占 tab）
        （资源/关于 → 设置，从结论页右上角进入）
```

理由：结论页答"你在这个位次能上什么档"，核验答"其中哪个专业值得读"。后者是前者的下钻，天然不该平级。

### 里程碑与验收

| 阶段 | 内容 | 验收（可演示，且不需要讲解） |
|---|---|---|
| **S0**（1–2 天） | 语义拆分（`alignment` / `reachability`）+ 证据门槛 + 降级 | 无校线时页面上**看不到**任何"一致/冲突"，只有"数据未覆盖" |
| **S1**（2 天） | 观点治理 + 去人格化 + 复核队列 | `/api/health` 能报"待复核观点 N 条" |
| **S2**（3–5 天） | 真实校线导入 → 位次趋势 → `OppositionPanel` 深色版 | 广东某校某组，观点"慎选" + 数据"位次 3 年降 1.2 万" → 冲突有据，能指着数字说 |
| **S3**（2 天） | 批量冲突排序 + 结论页下钻接线 | 扫一眼颜色分布能读出候选池矛盾密度 |
| **S4**（2 天） | 图谱扩量 + 志愿表状态点 | 图谱 ≥120 条，志愿表红灯数可见 |

**不做清单**（明确划掉，避免战线扩散）：
- ❌ 浅色皮肤整体迁移
- ❌ 3 tab 重构（改 3 格但保留串行语义）
- ❌ 引入 Pinia
- ❌ `--td-*` 变量覆盖
- ❌ 在没有校线数据前做对置版式

## 7. 一句话

「矛盾探测器」是对的，但要探测的是**观点与事实**的矛盾，不是**我们自己的两张表**的矛盾。现在这张表把"推荐→一致"写死了，版式越漂亮，越像在自证。**先让第二侧有数据，再让它并排。**
