# 官方数据年度采集指南（P0/P1）

> 产品对用户的承诺是「数据可靠、真实、准确」，而这套系统的可信度上限就是官方数据占比。
> 本指南回答三个问题：**每年要采什么、什么时候采、采到了怎么喂进系统**。
> 配套设施：管理端「采集台账」页（31 省 × 年份 × 数据类矩阵）+ CLI 批量投喂 + 一键体检。

## 1. 采集对象（三类数据）

| 数据类 | 内容 | 来源 | 用途 |
| --- | --- | --- | --- |
| `control_lines` 省控线 | 各批次最低控制线（特招线/本科批/专科批） | 省考试院年度公告 | verdict 档位判定、跨年趋势 |
| `school_lines` 逐校投档表 | 普通类本科批逐校（逐专业组）投档最低分与位次 | 省考试院「投档情况表」 | 推荐/核验的院校级核心数据 |
| `rank_table` 一分一段表 | 分数 → 累计人数（本科档/专科档） | 省考试院成绩分布公告 | 分数↔位次换算、交叉校验基准 |

优先级：**逐校投档表 > 一分一段表 > 省控线**（省控线 2022–2026 已自持 662 行，逐校投档是当前最大缺口）。

## 2. 采集窗口（关键！）

各省考试院在 **6 月下旬（公布成绩）至 8 月上旬（各批次投档结束）** 陆续公布原表。
错过窗口后原表往往从首页撤下（链接可能仍有效但难以检索）。

建议节奏：
- **6 月底**：采省控线（最早公布）；同步采集一分一段表。
- **7 月中旬**：本科批投档表陆续发布，逐省跟进。
- **8 月上旬**：专科批收尾；对全年份做一次体检（见 §6）。
- 每采到一份，立即在管理端「采集台账」把对应格子标为「已采集/已落库」。

## 3. 原表长什么样

投档情况表通常是一个 xls/zip 附件，列名各省不同但语义一致，系统已支持常见写法
（`services/school_lines.py` 的 `HEADER_ALIASES`）：
「院校名称 / 院校」「投档最低分 / 最低分」「投档最低排位 / 最低位次」「院校专业组代码」等。

**只采普通类平行志愿投档表**；艺术类/体育类/提前批非平行志愿的口径不可比，不采。
拿到的 PDF 版先转成 XLSX（WPS/Excel 可直接打开多数 xls 附件；纯图片版人工转录，
转录规矩见 `backend/data/SOURCES.md` 的硬规矩——没列的值不臆造）。

## 4. 投喂步骤

### 4.1 管理端（推荐，日常用）
「校线导入」页 →「官方逐校投档线落库」上传 CSV/XLSX/JSON，**来源链接必填**
（缺链接的行整行拒收）。先「仅预览」看匹配率与拒收原因，再提交落库。

### 4.2 单文件 CLI
```bash
cd backend
python scripts/import_official_table.py 广东_2024_物理类.xlsx \
    --province 广东 --year 2024 --subject 物理类 --source-org 广东省教育考试院 \
    --source-url https://eea.gd.gov.cn/... --dry-run    # 先预览
# 确认无误后把 --dry-run 换成 --commit
```

### 4.3 批量投喂（整季收尾用）
把当季原表放进 `backend/data/official/`（JSON 文件自带 `meta` 块填
`year/province/subject/source_url`；CSV 用命令行参数兜底），然后：
```bash
python scripts/import_official_table.py --landing-dir backend/data/official --dry-run
python scripts/import_official_table.py --landing-dir backend/data/official --commit
```
汇总报告会给出每文件的落库/拒收数与跳过原因（多为缺来源链接）。

### 4.4 落库后自动发生的事
- 每行标 `data_source=official`，推荐/核验链路**官方口径优先**（同校同年估算行不再遮蔽官方行）；
- **位次交叉校验**：用该省当年一分一段表反查 `min_score→rank`，与原表位次偏差超 25% 的行
  在备注留痕「需人工复核」，落库不被阻断；
- **溯源台账** `data/official/sources.json` 记录文件 sha256、链接、行数；
- **原表留档** `data/official/archive/<sha256前缀>-<文件名>`（P2）——考试院链接失效后仍可复核。

## 6. 落库后的核对动作

1. **管理端「采集台账」**：对应格子应变绿（已落库）；台账状态说「已落库」但格子显示
   库内 0 行，说明数据没真正进库，先查导入报告。
2. **一键体检**（采集台账页底部）：看官方行数、交叉校验告警、跨年突变清单。
3. **跨年突变**：同校同专业组相邻两年位次变化超 50% 会列出清单——先核对是否抄错列
   （如把「最高分位次」抄成「最低分位次」），再确认是否扩招/改名等真实波动。

## 7. 状态口径（采集台账）

| 状态 | 含义 |
| --- | --- |
| 待采集 | 窗口到了还没拿到原表 |
| 已采集 | 原表到手（本地有文件），尚未落库 |
| 已落库 | 已走导入通道进库（库内实测行数 > 0 才可信） |
| 当年无公布 | 该省该年确实没有这类公布（如个别省不公布逐专业组投档） |

## 8. 数据准确性与体检（审核回归后口径）

体检（`GET /api/admin/data-quality`，管理端采集台账页）覆盖**全部数据来源**，
不只 official——库内 99.9% 是 estimated_real，只查官方行等于只体检了 0.1%：

| 检查项 | 口径 | 处置 |
| --- | --- | --- |
| 位次交叉校验 | `min_score` 经该省当年一分一段表反查（专科批用专科档累计、其余用本科档），偏差 >25% 告警 | 导入时写行备注「需人工复核」；体检全量复检 |
| 控线硬约束 | 本科批投档分 < 当年该省最低本科线、专科批 < 专科线（M15 型确定性错误，实测种子 14020 行：抓出 7 行位次交叉偏差 + 1 行控线违规（正是审核确证的 M15 案例：内蒙古大学 河北 本科批 431<477）） | 体检列出清单，人工复核后修正或拒收 |
| 跨年突变 | 同校同专业组相邻年位次变化 >50% | 体检列清单 |

诚实边界：体检是**监控**不是**自愈**——它把疑点算出来、写清楚，但不会自动改数。
对已落库的错误行，走管理端「校线导入」重新落正确口径（幂等按唯一键覆盖）。
