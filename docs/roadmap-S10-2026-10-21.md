## 1. 本轮推荐：S10-A「年度罗盘」前端页（P0，成本最低收益最高）

近五年省控线已落盘 + API 就绪，但用户在客户端看不到——价值没有兑现。

- **新页面**（或并入 graph 页 tab）：省份选择 → 年份切换（2022–2026）→ 物理类/历史类 ×
  普通一本/普通二本/专科 线值表格；
- **跨年对比**：同省同科类同档位五年走势（简单横条或折线，客户端可直接画）；
- **跨省对比**：同年不同省并排（注意口径提示：新高考综合省 vs 文理省）；
- 数据源直接读 `/api/admission/control-line-years` + `/control-lines`，无需新后端；
- 接入点建议：verdict/plan 页给「查看历年省控线」入口，图谱页加「省控线」分区；
- 每条数据展示来源链接（`source_url`）——延续数据溯源的产品人格。

工作量：约半天（页面 + 样式 + 模板测试用例）。

## 2. S10-B 志愿个数上限与组内专业排序（S9-C 补做，P0 产品完整性）

- 志愿表硬约束：按省配置志愿个数上限（如河南 45 个院校专业组、辽宁 112 个），超出阻止保存并提示；
- 组内专业排序 + 是否服从调剂标记（导出文本同步体现）；
- `plan.js` 的 `flattenPlan`/导出链路扩展，注意导出格式与真实志愿表字段对齐。

## 3. S10-C 一分一段表采集（P1，数据层第二梯队）

- 目标：把省控线落库时 `min_rank=0` 的位次补上（等位分换算、位次锚定都需要它）；
- 现实约束：一分一段表散在各省考试院站（部分为 PDF/JS 渲染），反爬不一，**逐省分批**；
- 建议先做 2–3 个代表省（如广东=物理/历史、河南=文理、浙江=综合一段二段）验证可行性，
  落盘形态沿用本次省控线的「年度 JSON + source_url」模式；
- 拿不到的省诚实缺省，不做推算（延续「官方行必须可溯源」的硬规矩）。

## 4. S10-D 部署上线（P1）

- H5 构建产物 + 后端（FastAPI + SQLite）打包部署，产出可分享链接；
- 部署前过一遍 `docs/deployment.md` 与多数据库配置（若用托管 PostgreSQL 正好实测 db_config 切换）；
- 上线后 health 端点 + 备份任务要跟着配置。

## 5. 长期候选（P2，记录在案不排期）

- **逐校投档线扩量**：14020 行 estimated_real 的年度更新流水线跑通一次完整周期（CI 已有骨架）；
- **等位分换算扩年**：`equiv` 目前依赖的曲线年份覆盖较窄，可吃一分一段数据红利；
- **管理端 db_config 实测 MySQL/PostgreSQL**：单测已覆盖，缺真实库演练；
- **E2E 冒烟**：客户端核心链路（输入位次 → 推荐 → 下钻 → 志愿表导出）一条自动化走查。

## 6. 纪律（不变）

- 官方数据必须带可点开 `source_url`，缺则整行拒收；`estimated_real` 永不自动升格官方。
- 位次口径：`min_rank` = 投档末位位次，数字越大门槛越低；余量跨年/跨批次不可直接相减。
- 测试：全新库跑全量（conftest 已自封闭）；沙箱禁用 `tmp_path`，用项目内 `.bk_tmp`。
- 推送：每次单独确认，tree SHA 校验。
- S9-A 一旦拿到真实原表，优先级自动升至当轮最高（当日可落地）。
